NOT PATCHED HERE, BUT WRAPPED: these builds drop HDF5's status, so every instance is
guarded from outside (`guardH5Status`: lib/sleap-io's `LUCID local patch (failed status)`,
loading/h5-status-guard.js). The guards replace `Module.get_dataset_data`,
`get_attribute_data`, `reclaim_vlen_memory`, `reclaim_vlen_memory_count`, the write calls,
`FS.write` and `File.prototype.close`. On a bump check those names, and that HDF5's automatic
error printing still goes to fd 2 and still stays quiet on a healthy save
(tests/e2e/slp-failed-write.mjs §0).

LOCAL PATCH (cold-read), in hdf5_util.js AND h5wasm.iife.js:
  WORKERFS's `stream_ops.read` reads a File one slice at a time with
  FileReaderSync. In a folder synced by Google Drive for desktop on macOS (File
  Provider), a file whose download is still in progress can hand back a slice
  with one or two 16 KiB pages of ZEROS and every other byte right (measured
  2026-10-19 on the proofread SLAP sessions; a warm read of the same file is
  always right). Nothing fails, so HDF5 parsed the zeros as data. The patch
  adds `lucidColdReadGuard`, called right after the slice is copied: every part
  of the read that came back all zero (per 4 KiB block, clipped to the read) is
  read again TOGETHER WITH THE 4 KiB BLOCK ON EACH SIDE OF IT, and re-read bytes
  are copied in only where the first read gave a zero byte; a re-read that
  still holds an all-zero part is checked the same way, at most three re-reads
  deep. A hole comes back as the real bytes; bytes that really are zero cost
  one small re-read. The neighbouring blocks are there because a run of zeros
  need not end on a block boundary: on 167 MB .slp files read cold (5-camera
  BM_JJ arena sessions, 2026-10-19) the first version of this patch, which
  re-read only the all-zero blocks, still parsed 15 of 15 files wrong, and all
  93 wrong blocks examined were the partly-zero block right after the run it
  had re-read. With the neighbours, 15 of 15 cold parses on three more sessions
  matched the file. Reads that THROW were never seen here (0 in ~645,000 cold
  reads, ~10 GB), so the patch has no retry for them. A read or a re-read that
  throws goes up through FS.read, where every worker that reads a user's .slp
  catches it (the `LUCID local patch (failed read)` in lib/sleap-io, the same
  rule in loading/slp-import-worker.js): the bytes are not known to be right,
  so the whole read fails. Counts are kept on
  `WORKERFS.lucidColdRead` ({rereads, recovered}); each recovery logs a
  `[h5wasm WORKERFS] … were read again` console warning.
  Grep `LUCID local patch (cold-read)`: one BEGIN/END block (the function,
  byte-identical in both files) plus the one-line call in each WORKERFS read.
  `tests/test-workerfs-cold-read.mjs` asserts both, exercises both builds, and
  fails on the unpatched files. Note `git diff` shows hdf5_util.js as binary
  (embedded wasm); the IIFE carries the same block in readable form.

LOCAL PATCH (full heap), in hdf5_util.js AND h5wasm.iife.js:
  embind's std::string `toWireType` doesn't check its `_malloc`. With h5wasm's heap
  full (2 GiB at most) it took address 0, and wrote the string's length and bytes from
  there, over HDF5's static data from byte 1024 on, with no error. Later calls of that
  module then failed in any way, such as "memory access out of bounds" in `new File`,
  or could have gone on with damaged tables. Now it throws `Out of memory in h5wasm`.
  Grep `LUCID local patch (full heap)`: one line in each file. The UTF-16 string type
  beside it has the same gap, and nothing in h5wasm passes one.
  Test: tests/e2e/slp-failed-write.mjs §1.
